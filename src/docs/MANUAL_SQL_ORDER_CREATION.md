# Manual SQL Order Processing

This runbook creates one order manually for local or controlled test use. It uses the current schema, where the order service stores checkout/order data in MySQL and the product service stores stock reservations in PostgreSQL.

Do not use this as a replacement for the checkout API in production. Direct SQL bypasses RabbitMQ events, payment-intent creation, stock validation, outbox/inbox processing, read-model updates, and audit behavior.

## 1. Values for this test order

Use UUIDs that do not already exist. The product and checkout values below are from the example request.

```sql
-- MySQL and PostgreSQL values
SET @checkout_id = '720c65cf-acba-11f1-a205-8e985e8a7e37';
SET @product_id = 'a496b663-d318-45a4-86db-24c736fb487d';
SET @variant_id = NULL; -- Set this when the product has a sellable variant.
SET @user_id = '00000000-0000-0000-0000-000000000001';
SET @correlation_id = UUID();
SET @reservation_id = UUID();
SET @order_id = UUID();
SET @payment_id = UUID(); -- Use a real payment id only when simulating payment completion.

SET @quantity = 2;
SET @unit_price = 42.93;
SET @line_total = @quantity * @unit_price;
SET @shipping_total = 0.00;
SET @order_total = @line_total + @shipping_total;
```

The `@name` variables above are MySQL session variables. In PostgreSQL, replace them with literal values or use a `DO $$ ... $$` block. Do not expect variables created in one database connection to be available in another connection.

Before inserting, verify that the product exists in the product database and that the checkout/order UUIDs are unused:

```sql
-- PostgreSQL product database
SELECT id, name, sku, stock, "warehouseStockMirror"
FROM products
WHERE id = 'a496b663-d318-45a4-86db-24c736fb487d';

-- MySQL order database
SELECT id FROM checkout_sessions
WHERE id = '720c65cf-acba-11f1-a205-8e985e8a7e37';

SELECT order_id FROM orders
WHERE order_id = '00000000-0000-0000-0000-000000000000';
```

If a variant is used, also verify it in PostgreSQL:

```sql
SELECT id, "productId", sku, "effectiveSellingPrice", stock
FROM product_variants
WHERE id = '<variant-uuid>'
  AND "productId" = 'a496b663-d318-45a4-86db-24c736fb487d';
```

## 2. Create the checkout in MySQL

Run this section against the order-service MySQL database. The checkout starts in `PENDING_STOCK` (`status_id = 1`).

```sql
START TRANSACTION;

INSERT INTO checkout_sessions (
    id,
    user_id,
    status_id,
    correlation_id,
    reservation_id,
    payment_id,
    total,
    shipping_total,
    idempotency_key,
    expire_at,
    created_at,
    updated_at
) VALUES (
    @checkout_id,
    @user_id,
    1,
    @correlation_id,
    @reservation_id,
    NULL,
    @order_total,
    @shipping_total,
    CONCAT('manual-', @checkout_id),
    DATE_ADD(UTC_TIMESTAMP(), INTERVAL 30 MINUTE),
    UTC_TIMESTAMP(),
    UTC_TIMESTAMP()
);

INSERT INTO checkout_items (
    checkout_id,
    product_id,
    variant_id,
    qty,
    price,
    line_total,
    currency,
    created_at,
    updated_at
) VALUES (
    @checkout_id,
    @product_id,
    @variant_id,
    @quantity,
    @unit_price,
    @line_total,
    'USD',
    UTC_TIMESTAMP(),
    UTC_TIMESTAMP()
);

COMMIT;
```

The product snapshot columns on `checkout_items` are nullable, but a real checkout normally fills them from the product validation response. For a realistic test, populate `product_slug`, `product_title`, `product_sku`, `category_id`, `shop_id`, `image_url`, and `available_stock` from the product database response in the same insert.

## 3. Create the stock reservation in PostgreSQL

Run this section against the product-service PostgreSQL database. The reservation is linked by `checkoutId`; there is no foreign key across services.

```sql
BEGIN;

INSERT INTO order_stock_reservations (
    id,
    "checkoutId",
    "correlationId",
    status,
    reason,
    "expiresAt",
    "createdAt",
    "updatedAt"
) VALUES (
    '<reservation-uuid>',
    '720c65cf-acba-11f1-a205-8e985e8a7e37',
    '<correlation-id>',
    'RESERVED',
    NULL,
    NOW() + INTERVAL '30 minutes',
    NOW(),
    NOW()
);

INSERT INTO order_stock_reservation_items (
    id,
    "reservationId",
    "productId",
    "variantId",
    quantity
) VALUES (
    gen_random_uuid(),
    '<reservation-uuid>',
    'a496b663-d318-45a4-86db-24c736fb487d',
    NULL,
    2
);

COMMIT;
```

Replace `<reservation-uuid>` with the same UUID stored in MySQL `checkout_sessions.reservation_id`. Replace `<correlation-id>` with the value stored in `checkout_sessions.correlation_id`. If `gen_random_uuid()` is unavailable, enable the `pgcrypto` extension or provide another UUID generated by the application.

The `product.stock.reserved` consumer performs two MySQL transitions: `PENDING_STOCK` (`1`) to `STOCK_CONFIRMED` (`2`), then to `PENDING_PAYMENT` (`6`) after the payment intent is created. SQL cannot create that payment intent, so perform the database transitions explicitly only for a controlled test:

```sql
-- MySQL order database
UPDATE checkout_sessions
SET status_id = 2,
        reservation_id = '<reservation-uuid>',
        updated_at = UTC_TIMESTAMP()
WHERE id = '720c65cf-acba-11f1-a205-8e985e8a7e37'
    AND status_id = 1;

UPDATE checkout_sessions
SET status_id = 6,
        updated_at = UTC_TIMESTAMP()
WHERE id = '720c65cf-acba-11f1-a205-8e985e8a7e37'
    AND status_id = 2;
```

## 4. Complete payment and create the order in MySQL

This simulates the `payment.completed` consumer. Only run it when you have deliberately chosen a payment id for the test. A real payment service will not know about this manual row.

```sql
START TRANSACTION;

UPDATE checkout_sessions
SET status_id = 7, -- CONFIRMED
    reservation_id = '<reservation-uuid>',
    payment_id = '<payment-uuid>',
    updated_at = UTC_TIMESTAMP()
WHERE id = '720c65cf-acba-11f1-a205-8e985e8a7e37';

INSERT INTO orders (
    order_id,
    checkout_id,
    reservation_id,
    payment_id,
    status_id,
    created_at,
    updated_at
) VALUES (
    '<order-uuid>',
    '720c65cf-acba-11f1-a205-8e985e8a7e37',
    '<reservation-uuid>',
    '<payment-uuid>',
    7, -- CONFIRMED
    UTC_TIMESTAMP(),
    UTC_TIMESTAMP()
);

UPDATE orders
SET status_id = 4, -- PAID
    updated_at = UTC_TIMESTAMP()
WHERE order_id = '<order-uuid>'
  AND checkout_id = '720c65cf-acba-11f1-a205-8e985e8a7e37'
  AND status_id = 7;

COMMIT;
```

The application normally confirms the checkout, creates the `orders` row as `CONFIRMED`, attaches the payment, and then marks the order `PAID` when it consumes `payment.completed`. Do not run this section if the payment consumer has already created the order. The `checkout_id` column is unique in `orders`.

## 5. Advance the order through fulfillment states

Use one statement at a time and verify the previous state before changing it. The current status ids are:

| ID | Name |
| ---: | --- |
| 1 | PENDING_STOCK |
| 2 | STOCK_CONFIRMED |
| 3 | FAILED_STOCK |
| 4 | PAID |
| 5 | FAILED_PAYMENT |
| 6 | PENDING_PAYMENT |
| 7 | CONFIRMED |
| 8 | CANCELLED |
| 9 | PARTIALLY_FULFILLED |
| 10 | FULFILLED |
| 11 | PARTIALLY_REFUNDED |
| 12 | REFUNDED |
| 13 | READY_FOR_FULFILLMENT |
| 14 | SHIPPED |

```sql
-- Product confirmed the reservation.
UPDATE orders
SET status_id = 13, updated_at = UTC_TIMESTAMP()
WHERE order_id = '<order-uuid>'
  AND status_id IN (4, 7);

-- Optional: shipment created by an admin.
UPDATE orders
SET status_id = 14,
    courier_code = 'manual-courier',
    courier_name = 'Manual Test Courier',
    courier_phone = '+0000000000',
    tracking_number = 'MANUAL-TEST-001',
    tracking_url = NULL,
    shipment_created_at = UTC_TIMESTAMP(),
    updated_at = UTC_TIMESTAMP()
WHERE order_id = '<order-uuid>'
  AND status_id = 13;
```

If the stock reservation is confirmed manually, update PostgreSQL separately:

```sql
UPDATE order_stock_reservations
SET status = 'CONFIRMED', "updatedAt" = NOW()
WHERE id = '<reservation-uuid>'
  AND status = 'RESERVED';
```

Do not update a reservation to `CONFIRMED` unless the requested quantity has actually been reserved. Do not insert into the old `stock_reservations` or `stock_reservation_items` tables; those warehouse tables were removed.

## 6. Verify all tables

MySQL:

```sql
SELECT
    cs.id AS checkout_id,
    cs.user_id,
    cs.status_id AS checkout_status_id,
    checkout_status.name AS checkout_status,
    cs.reservation_id,
    cs.payment_id,
    cs.total,
    ci.product_id,
    ci.variant_id,
    ci.qty,
    ci.price,
    ci.line_total,
    o.order_id,
    o.status_id AS order_status_id,
    order_status.name AS order_status,
    o.tracking_number
FROM checkout_sessions cs
JOIN checkout_items ci ON ci.checkout_id = cs.id
LEFT JOIN orders o ON o.checkout_id = cs.id
LEFT JOIN statuses checkout_status ON checkout_status.id = cs.status_id
LEFT JOIN statuses order_status ON order_status.id = o.status_id
WHERE cs.id = '720c65cf-acba-11f1-a205-8e985e8a7e37';
```

PostgreSQL:

```sql
SELECT
    r.id AS reservation_id,
    r."checkoutId",
    r.status,
    r."correlationId",
    ri."productId",
    ri."variantId",
    ri.quantity
FROM order_stock_reservations r
JOIN order_stock_reservation_items ri ON ri."reservationId" = r.id
WHERE r."checkoutId" = '720c65cf-acba-11f1-a205-8e985e8a7e37';
```

## 7. Cleanup a manual test order

Delete the PostgreSQL child rows before the reservation parent, then delete the MySQL order and checkout. Use the exact test UUIDs only:

```sql
-- PostgreSQL
BEGIN;
DELETE FROM order_stock_reservation_items
WHERE "reservationId" = '<reservation-uuid>';
DELETE FROM order_stock_reservations
WHERE id = '<reservation-uuid>'
  AND "checkoutId" = '720c65cf-acba-11f1-a205-8e985e8a7e37';
COMMIT;
```

```sql
-- MySQL
START TRANSACTION;
DELETE FROM orders
WHERE order_id = '<order-uuid>'
  AND checkout_id = '720c65cf-acba-11f1-a205-8e985e8a7e37';
DELETE FROM checkout_sessions
WHERE id = '720c65cf-acba-11f1-a205-8e985e8a7e37';
COMMIT;
```

Deleting the checkout cascades to `checkout_items`. If any event consumer has already processed this order, also clean up or replay the related outbox/read-model data according to that service's own procedures.
